Top Technical Questions Expected

1. Explain hybrid mode architecture and benefits
Hybrid mode separates the Control Plane (CP) from Data Planes (DPs). CP handles config/admin with PostgreSQL, DPs are stateless and proxy traffic. Benefits: DPs survive CP outages (LMDB cache), horizontal DP scaling, security isolation (Admin API not exposed on DP), easier upgrades. Communication via mTLS on port 8005.
2. Customer reports intermittent 502s — investigation walkthrough
Gather: When did it start? Specific routes or all? Any recent changes? Frequency?
Isolate: Check Kong error logs, upstream health (curl localhost:8001/upstreams/<name>/health), check if all targets are healthy.
Diagnose: 502 means upstream returned error or connection failed. Check: upstream down, SSL mismatch to upstream, plugin error in response phase, buffer too small for headers, DNS resolution failures.
Verify: X-Kong-Upstream-Latency header, curl -v directly to upstream bypassing Kong.
3. Rate limiting not working across nodes
Root cause: Using local strategy — each node counts independently.
Fix: Switch to redis strategy for shared counters across nodes. Check: Redis connection, config.redis.host/config.redis.port (3.6+; config.redis_host is the legacy field), firewall rules. With limit_by=consumer and no identified consumer, Kong falls back to limiting by client IP. Watch config.anonymous: all anonymous requests share one consumer bucket.
4. Plugins that don't work in hybrid/DB-less mode
Hybrid: OAuth2 (requires DB writes on DP), cluster-strategy rate limiting (needs shared DB state).
DB-less: Any plugin that requires writes — OAuth2, session (DB store), response-ratelimiting (cluster).
5. Active vs passive health checks
Active: Kong periodically probes targets (configurable interval, path, thresholds). Can both mark targets unhealthy AND re-enable them.
Passive: Monitors actual traffic responses. Can mark targets unhealthy but cannot re-enable them — requires active checks or manual API call to re-enable.
6. Plugin execution order conflicts
Plugins execute by priority (higher number = earlier). If auth plugin (1250) runs before rate limiting (910), unauthenticated requests are rejected before consuming rate limit quota. If you need rate limiting BEFORE auth (to protect from DDoS), use pre-function (1M priority) with custom logic or adjust plugin order via ordering field (Enterprise only).
7. CORS preflight handling
Enable the CORS plugin. Configure origins, methods, headers, credentials. For preflight (OPTIONS): Kong responds directly without forwarding to upstream. Note: browsers reject Access-Control-Allow-Origin: * when credentials are sent. Kong handles this: with origins: * and credentials: true it reflects the request Origin (and adds Vary: Origin). For security, still list explicit origins — reflecting every origin with credentials is effectively "allow any site".
8. WebSocket proxying requirements
Kong supports WebSocket natively. Requirements: route must match the upgrade request, Upgrade: websocket and Connection: Upgrade headers must pass through. Works on ordinary http/https services. For long-lived connections, raise the Service's read_timeout and write_timeout (ms, default 60000). The ws/wss protocols are optional and Enterprise-only (for WebSocket-aware plugins).
9. gRPC proxying
Requires HTTP/2 end-to-end. Set service protocol to grpc or grpcs. Route must have protocols: ["grpc", "grpcs"]. Client connects via HTTP/2 to Kong, Kong forwards gRPC to upstream. Use grpc-gateway plugin to transcode REST to gRPC.
10. How to troubleshoot a custom Lua plugin
Steps: Check /usr/local/share/lua/5.1/kong/plugins/<name>/ for handler.lua and schema.lua. Enable debug logging (log_level = debug). Use kong.log.inspect() in plugin code. Check error logs for stack traces. Validate schema with kong config parse. Test in DB-less mode with declarative config for faster iteration.

Troubleshooting Framework

Use this structure in EVERY troubleshooting answer:

1
Gather — What error? When? Intermittent or constant? What changed?
2
Reproduce — Can you consistently trigger it? Specific users/routes/times?
3
Isolate — Client → Gateway → Network → Upstream? Disable plugins one by one.
4
Diagnose — Logs, metrics, tcpdump, curl at each layer.
5
Resolve — Fix + verify.
6
Document — Root cause, resolution, prevention (knowledge article).

Common Troubleshooting Scenarios

502 Bad Gateway

Causes:

  • Upstream service down or not reachable
  • SSL/TLS mismatch to upstream (wrong cert, protocol version)
  • Plugin error in response phase
  • Connection refused (wrong port, firewall)
  • Buffer too small for response headers (proxy_buffer_size)

Debug: curl localhost:8001/upstreams/<name>/health, check error.log, try direct curl to upstream.

503 Service Unavailable

Causes:

  • All targets unhealthy (health check threshold breached)
  • DNS resolution failure for upstream
  • Server overloaded
  • Circuit breaker tripped (if configured)

Debug: Check target health status, DNS resolution, upstream resource usage.

Rate Limiting Issues

Causes:

  • Using local strategy — not shared across nodes
  • Redis connection failure — plugin fail-opens (allows all traffic)
  • Wrong identifier — IP behind load balancer (use X-Forwarded-For)
  • limit_by=consumer with no identified consumer falls back to client IP; with config.anonymous, all anonymous requests share one consumer bucket

Fix: Use redis strategy, verify Redis connectivity, check X-RateLimit-* response headers.

Auth Failures (JWT/Key-Auth)

Causes:

  • Token expired (check exp claim)
  • No matching jwt credential for the token's iss (or key_claim_name) claim
  • Wrong secret or rsa_public_key on the consumer's jwt credential
  • Token rejected by claims_to_verify (exp/nbf) or exceeds maximum_expiration
  • Clock skew between client and Kong
  • OIDC (Enterprise openid-connect plugin): issuer mismatch or JWKS endpoint unreachable
  • config.anonymous misconfigured — allowing unintended access

Debug: Decode JWT at jwt.io, check clock sync, verify the consumer's jwt credential (key/secret); for openid-connect, verify the issuer/JWKS URL is reachable from the Kong pod.

Hybrid Mode Issues

Causes:

  • CP/DP version mismatch (DP minor must be <= CP minor)
  • mTLS certificate expired
  • Stale DP config (check curl localhost:8001/clustering/data-planes)
  • Using unsupported plugins (OAuth2, cluster rate limiting)

Debug: Check DP logs for connection errors, verify cert expiry with openssl, compare versions.
