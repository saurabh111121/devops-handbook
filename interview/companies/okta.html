JWT validation checklist (recite this):
  1. Signature — verify with issuer's public key from JWKS (/.well-known/jwks.json), selected by kid
  2. iss matches expected issuer · aud matches your client/API
  3. exp not expired; nbf/iat sane (allow small clock skew)
  4. nonce matches (interactive flows) · alg is expected — reject alg:none and RS256→HS256 downgrade
JWT payload is base64url-encoded, NOT encrypted — readable by anyone. The signature provides integrity, not secrecy.

SAML 2.0

SP-Initiated SSO Flow
 1. User → SP: requests protected resource
 2. SP → browser: redirect with SAMLRequest (AuthnRequest) to IdP SSO URL
 3. browser → IdP: delivers AuthnRequest
 4. IdP: authenticates user (if no existing session)
 5. IdP → browser: HTML form auto-POSTs SAMLResponse to SP's ACS URL
 6. browser → SP (ACS URL): POSTs signed SAMLResponse
 7. SP: validates signature, conditions, audience → creates session → access
  • IdP issues the signed assertion; SP consumes it. Browser brokers all redirects (front-channel).
  • SP needs: IdP public certificate, ACS endpoint, IdP sign-in URL.
  • ForceAuthn=true (the Okta SAML checkbox) re-prompts for credentials even with a live session — used for step-up.
  • RelayState preserves deep-link context across SP-initiated flow (SAML's analog to OAuth state).
  • Single Logout (SLO) propagates logout to all SP sessions — flakier than SSO.
  • Nuance: "SP never talks to IdP" is only true for front-channel; the HTTP Artifact Binding uses a back-channel SOAP call.

WS-Federation · LDAP · Azure AD

WS-Fed & LDAP

  • WS-Fed: older Microsoft/ADFS XML federation (WS-* family); STS issues tokens. Legacy — migrate to SAML/OIDC.
  • LDAP: protocol to query a directory (AD/OpenLDAP). Ports 389/636. AuthN = a bind with the user's DN + password (often search-then-bind).
  • DN: cn=jdoe,ou=Users,dc=example,dc=com
  • Okta connects to on-prem AD/LDAP via an agent; know delegated auth vs password sync.

Azure AD / Entra ID

  • Microsoft's cloud IdP (renamed Entra ID); supports OIDC, OAuth2, SAML, WS-Fed.
  • Common as an inbound IdP federated into Okta.
  • Concepts: tenant, app registration, enterprise application, service principal, Conditional Access, MSAL, Graph API, v1.0 vs v2.0 endpoints.
  • Typical ticket: federated login into Okta fails → check protocol config, certs, claim/attribute mapping, issuer/audience.

Encryption vs Hashing vs Encoding — classic trick question

Reversible?PurposeExample
EncodingYes, no keyFormat/transportBase64, URL-encoding
EncryptionYes, with keyConfidentialityAES, RSA
HashingNo (one-way)Integrity / passwordsSHA-256, bcrypt
  • Base64 is NOT encryption — it's encoding. JWTs are base64url-encoded, not encrypted.
  • Passwords: never encrypt/plaintext — hash + salt with bcrypt/scrypt/Argon2.
  • TLS: asymmetric crypto bootstraps the handshake, then symmetric session keys for bulk data.
  • Signing proves who sent it + integrity (private key); encryption hides content. JWT/SAML use signing.
  • SameSite cookies: SameSite=None; Secure needed for cross-site SSO/silent-auth; 3rd-party cookie blocking breaks iframe flows.
  • CORS: browser-enforced; server must send Access-Control-Allow-*. Common SPA/auth ticket.

Top Technical Questions Expected

1. What's the difference between authentication and authorization?
AuthN = verifying who you are (login, MFA). AuthZ = what you're allowed to do (scopes, roles). You authenticate first, then authorize. HTTP: 401 = AuthN failure, 403 = AuthZ failure. Protocols: OIDC/SAML = authN, OAuth 2.0 = authZ.
2. OAuth 2.0 vs OIDC? (asked repeatedly)
OAuth 2.0 is an authorization framework for delegated API access — it doesn't tell you who the user is. OIDC is a thin identity layer on top of OAuth that adds authentication via the ID token (a JWT), plus the /userinfo endpoint and discovery. The openid scope triggers OIDC.
3. Walk me through the authorization code flow with PKCE.
Redirect to /authorize with response_type=code, client_id, redirect_uri, scope, state, and a code_challenge. User authenticates → 302 back with a one-time code. Client POSTs to /token with the code + code_verifier over a back-channel → receives access/ID/refresh tokens → calls API with Authorization: Bearer. PKCE protects public clients from auth-code interception by binding the redemption to the client that started the flow.
4. Why is the implicit flow insecure / deprecated?
It returns tokens directly in the URL fragment — exposed in browser history, referer headers, and logs, with no client authentication. Auth code + PKCE returns a one-time code exchanged server-side instead. Always recommend auth code + PKCE.
5. ID token vs access token? Opaque vs JWT?
ID token = authentication, audience is the client, always a JWT, client reads it. Access token = authorization for the API, audience is the resource server. From the client's view the access token is opaque "gibberish," but it's not required to be — Okta can issue JWT access tokens. Opaque tokens → introspection call to the AS; JWT → self-validate via JWKS (no network call, but harder to revoke).
6. What do state and nonce protect against?
state = CSRF protection on the redirect + carries app state; always validate it round-trips. nonce = ID-token replay protection, echoed into the token and validated by the client.
7. What is SAML and when would you use it over OIDC?
XML-based browser SSO between an IdP and SP. Use SAML for enterprise/workforce web SSO; use OIDC (JSON/JWT on OAuth) for modern SPA/mobile/API. Both do federation/SSO.
8. What does forced authentication (ForceAuthn) do in Okta SAML?
It forces the IdP to re-prompt for credentials even if an SSO session already exists — used for step-up auth on sensitive apps. If a customer complains users are re-prompted every time, check whether ForceAuthn is enabled.
9. Is Base64 encryption? How do you store passwords?
No — Base64 is reversible encoding with no key. Encryption needs a key (AES/RSA); hashing is one-way. Passwords must be hashed + salted with a slow algorithm (bcrypt/scrypt/Argon2), never encrypted or stored plaintext.
10. Does fetch reject on a 401/500? How would you write the call?
No — fetch only rejects on network failure; a 4xx/5xx resolves normally, so you must check res.ok/res.status before .json(). Also: the token endpoint expects application/x-www-form-urlencoded, not JSON — a very common integration bug.

Troubleshooting Framework

Narrate this structure in EVERY troubleshooting answer:

1
Clarify & Reproduce — Exact error/code? When did it start? Scope (one user vs all, one app vs all)? What changed (deploy, cert, config)?
2
Isolate the layer — Client/browser → network → IdP/Auth server → resource server/API → directory. Bisect the request flow.
3
Hypothesize — List likely causes ranked by probability + ease of checking.
4
Test one variable — Decode the token, check the status code, diff working vs failing config.
5
Resolve & Verify — Root cause (not symptom), apply fix, confirm with customer.
6
Document & Prevent — KB article, proactive alerting, clear communication.

Common Troubleshooting Scenarios

SSO suddenly broke for ALL users this morning

Think: "all users + sudden" → systemic change, not user-specific config.

Causes:

  • Expired/rotated SAML signing certificate (the textbook mass-outage cause)
  • IdP metadata changed, clock skew, a deploy on the SP, expired API credential

Debug: Decode the SAMLResponse (SAML-tracer), check signature + cert validity dates, correlate with "what changed at that timestamp." Fix: rotate cert, re-exchange metadata; prevent with cert-expiry monitoring.

Login redirects in an infinite loop

Causes:

  • Session cookie blocked (SameSite / third-party cookies) — most common modern cause
  • Missing Secure on HTTPS, clock skew, state/nonce mismatch, misconfigured redirect_uri
  • App not persisting the session

Debug: Network tab — is the session cookie set or blocked? Is each redirect re-hitting /authorize? Check SameSite=None; Secure for cross-site.

API returns 401 even with a token

401 = authentication problem with the token itself.

  • Token expired (exp), wrong audience (aud ≠ this API), wrong issuer (iss)
  • Signature invalid (stale JWKS / key rotation), wrong header/format, sandbox token vs prod API

Debug: Decode the token at jwt.io → inspect aud, iss, exp, alg; confirm Authorization: Bearer <token> formatting.

API returns 403 for SOME users only

403 = authenticated but not authorized → scopes/roles/permissions, not token validity.

  • Missing scope/permission on the token, missing group/role claim
  • Authorization policy excludes them, attribute/claim mapping wrong

Debug: Decode a working vs failing user's tokens, diff the scopes/roles/groups claims; check the authorization policy + group membership.

App works in Okta Preview but fails in Production (invalid_grant)

A reported real interview scenario. Causes to enumerate:

  • Wrong issuer / authorization server per environment
  • redirect_uri not registered in the prod app
  • client_id/secret swapped between envs
  • Authorization code reused or expired (codes are one-time, short TTL)
  • Clock skew on the token time window; PKCE code_verifier ≠ code_challenge

Debug: Diff prod vs preview config, decode the failing /token response JSON, check the code's age and single-use.

SPA: "blocked by CORS policy"

Browser-enforced; the SPA's origin isn't allowed by the server it calls.

  • Origin not added to allowed origins/CORS list on the tenant/app
  • Calling the wrong endpoint, preflight (OPTIONS) failing, credentials mode mismatch

Debug: Network tab → failing OPTIONS preflight + Access-Control-Allow-Origin response; add the exact origin (scheme+host+port) to the allowlist.

Decode a JWT in plain JS (be ready to write this)
function decodeJwt(token) {
  const [h, p] = token.split(".");
  const dec = b64 => JSON.parse(atob(b64.replace(/-/g,"+").replace(/_/g,"/")));
  return { header: dec(h), payload: dec(p) };
}
// Only DECODES (base64url) — signature is verified server-side via JWKS, not here.
const isExpired = payload.exp * 1000 < Date.now();
