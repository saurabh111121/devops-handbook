First triage question: classic or serverless? On classic compute, the customer's IAM, quotas, subnets, NSG/SGs, SCPs and firewalls are all possible failure points, and you have the Spark UI and cluster logs. On serverless, the infra belongs to Databricks, networking goes through NCCs and egress controls, and you have the query profile and system tables. If serverless works and classic does not, look at the customer's network or cloud account first.

Secure cluster connectivity (SCC)

  • Default for all new workspaces. Classic nodes have no public IPs and the VPC has no open inbound ports.
  • Each cluster opens an outbound 443 tunnel to the SCC relay. The control plane sends cluster commands down that tunnel.
  • Azure calls it No Public IP (NPIP): ARM enableNoPublicIp, default true from API 2024-05-01. Upgrading an existing workspace means stopping all compute first, and it can take 15+ min.
  • Allowlist relay FQDNs, not IPs.

PrivateLink

  • AWS: front-end (user → workspace) and back-end (compute → control plane). Back-end needs two interface endpoints: SCC relay + workspace REST API, with "Enable private DNS name" on. Private Access Settings (PAS) can be shared per region. Needs customer-managed VPC, SCC, Enterprise tier, VPC CIDR /25+.
  • Azure: inbound (front-end), outbound (serverless via NCC), classic (back-end). Sub-resources: databricks_ui_api, browser_authentication, general_access (Beta), service_direct. Needs Premium, VNet injection, SCC.
  • Azure pitfall: one browser_authentication endpoint per region per private DNS zone. Deleting the workspace that hosts it breaks SSO for every workspace in the region. Use a dedicated "private web auth" workspace.
  • NCC limits (Azure): 20 per region per account, 50 workspaces per NCC, 100 private endpoints per region.
Workspace storage: Docs say "Do not delete or modify the workspace storage in your cloud account." A bucket policy or lifecycle rule on the root bucket breaks notebook revisions and results. DBFS root and mounts are a "deprecated pattern and not recommended by Databricks".

UC facts to have ready

  • Privileges inherit downward and nothing is granted by default. Missing USE CATALOG / USE SCHEMA is the most common gap.
  • Managed storage location can be set at metastore (optional), catalog or schema level.
  • UC auto-enablement for new workspaces started 8 Nov 2023.
  • MSCK REPAIR TABLE ... SYNC METADATA resyncs external-table metadata changed outside UC.
  • Do not give non-UC identities direct access to managed storage.
  • Lineage: automatic to column level in system.access.table_lineage / column_lineage. None before 1 Sept 2024, not kept across renames, no RDDs or global temp views.

Row filters, column masks, ABAC

  • ALTER TABLE t SET ROW FILTER f ON (col); ALTER TABLE t ALTER COLUMN c SET MASK m.
  • DBR below 12.2 LTS "fail securely and return no data".
  • Dedicated mode needs 15.4 LTS+ with serverless enabled (runs through serverless FGAC). Read-only on 15.4-16.2, writes need 16.3+.
  • Not on views. No time travel or clones on protected tables.
  • Docs advise spark.sql.ansi.enabled=true, because failed casts become NULL and filters can return the wrong rows.
  • ABAC policies (catalog/schema level, governed tags) are recommended at scale. Table owners cannot override them.

Compute policies & init scripts

  • Compute policies (called "cluster policies" in APIs) fix or restrict attributes, cap cost and resources per user, and enforce up to 500 libraries. Lowering "max per user" does not terminate existing clusters.
  • Init scripts: cluster-scoped (recommended) and global (admin-only; run before cluster-scoped; Dedicated/No-isolation only).
  • DBFS init scripts and legacy global/cluster-named scripts are end-of-life.
  • Store them in a UC volume (DBR 13.3 LTS+), workspace files (11.3 LTS+, 500 MB limit), or cloud storage.
  • Serverless: no compute-scoped init scripts.

Identity & auth

  • Account-centric. Identity federation is on by default for new workspaces and cannot be disabled.
  • Automatic identity management (Entra ID, Okta) recommended; account-level SCIM is the fallback, workspace SCIM is legacy. SCIM does not support nested groups; Azure automatic identity management does.
  • Provisioned to account ≠ workspace access. Assign the user or group to the workspace.
  • Auth: OAuth token federation (recommended), OAuth M2M for service principals, OAuth U2M, PATs (legacy, discouraged).
  • Unified auth env vars: DATABRICKS_HOST, DATABRICKS_ACCOUNT_ID, DATABRICKS_CLIENT_ID, DATABRICKS_CLIENT_SECRET, or ~/.databrickscfg.
  • SSO is account-level (SAML 2.0 / OIDC). Emergency access for up to 20 users (password + security key).
  • A rotated SCIM token keeps the old one valid for 24 h. Account limits: 10,000 users+SPs / 5,000 groups for accounts created before 17 Nov 2025; 50,000 / 10,000 for accounts created on or after that date; raisable via the account team. Per-workspace cap: 10,000 users+SPs / 5,000 groups.

Skew playbook

  • AQE skew-join applies only to shuffle-based joins (sort-merge and shuffle hash), never broadcast joins, and not to aggregations. FULL OUTER gets no skew handling; LEFT/RIGHT OUTER only on the preserved side.
  • Lower skewedPartitionFactor / ThresholdInBytes if hot partitions are below 256 MB.
  • spark.sql.adaptive.forceOptimizeSkewedJoin (default false) forces it even with an extra shuffle.
  • Find the hot key (often NULL or 'UNKNOWN'), salt + two-stage aggregation, broadcast the small side.
  • REBALANCE hint on writes (ignored when AQE is off). Liquid clustering if skew comes from the table layout.

Structured Streaming essentials

  • Triggers: default (≈0 ms), processingTime, availableNow, once (deprecated since 11.3 LTS), realTime. Continuous is NOT supported on Databricks.
  • One checkpointLocation per query. Changing stateful operators, sources/topics or sink type needs a new checkpoint. Filters, rate limits and trigger interval are safe to change.
  • DBR 18.2+: spark.sql.streaming.queryEvolution.enableSourceEvolution allows source add/remove (cannot be undone).
  • Kafka: Spark does not commit offsets to Kafka, so consumer-group lag tools mislead. Read lag from avgOffsetsBehindLatest / maxOffsetsBehindLatest / estimatedTotalBytesBehindLatest. startingOffsets only applies to a new query. failOnDataLoss defaults to true.
  • Auto Loader: cloudFiles.schemaEvolutionMode defaults to addNewColumns when no schema is provided, so the stream stops on a new column by design. With a user-supplied schema the default is none (no evolution, no failure; new columns are dropped unless rescued data is enabled). Restart with job retries. maxFilesPerTrigger defaults to 1000.

Layout & maintenance

  • Liquid clustering (CLUSTER BY, up to 4 keys; CLUSTER BY AUTO needs predictive optimization) replaces partitioning + ZORDER and cannot be combined with them. GA on DBR 15.4 LTS+. OPTIMIZE is incremental. OPTIMIZE FULL (16.0+) reclusters everything and can take hours. 18.1+ adds REPLACE PARTITIONED BY WITH CLUSTER BY.
  • Z-ORDER is not idempotent and weakens with each extra column. Predictive optimization never runs it.
  • Data skipping uses stats on the first 32 columns (delta.dataSkippingNumIndexedCols / dataSkippingStatsColumns). Changing this does not recompute existing stats.
  • Small files: optimized writes + auto compaction (always on for MERGE/UPDATE/DELETE). Autotuning targets 256 MB files for tables under 2.56 TB.
  • Predictive optimization: runs OPTIMIZE, VACUUM, ANALYZE automatically. Default on, UC managed tables only, Premium+, DBR 12.2 LTS+.

VACUUM, RESTORE, deletion vectors

  • VACUUM default 7 days. spark.databricks.delta.retentionDurationCheck.enabled (true) blocks shorter retention. Turning it off is a safety-protection change, so get explicit sign-off. DRY RUN lists up to 1,000 files. LITE (16.1+) fails with DELTA_CANNOT_VACUUM_LITE if the log was pruned.
  • DBR 18.0+: VACUUM ignores the RETAIN argument except 0 HOURS, so RETAIN 24 HOURS silently uses the table's delta.deletedFileRetentionDuration. Set the table property instead.
  • RESTORE TABLE t TO VERSION AS OF n needs MODIFY and cannot reach vacuumed files. It is a data-changing commit, so downstream streams may see duplicates.
  • Deletion vectors: rows are marked removed, not rewritten. To physically erase (GDPR): DELETE → REORG TABLE ... APPLY (PURGE) → VACUUM past purge time. Also purge upstream (Kafka, landing files, OLTP).
  • Row-level concurrency: DBR 14.3 LTS+, unpartitioned, DVs enabled.

Lakeflow pipelines — the rule behind many tickets

Dataset functions must only return a DataFrame. No collect(), count(), toPandas(), save(), saveAsTable() or start() inside definitions, because the source is evaluated several times during planning. Side effects run repeatedly, which shows up as "duplicate writes in prod". Use sinks / foreach_batch_sink for external writes. The pipeline event_log is the primary diagnostic. Concepts: streaming tables, materialized views, temporary views, flows (Append, Update, AUTO CDC), expectations (warn / drop / fail).

8. Platform Troubleshooting Scenario Bank

Read the termination type first. It tells you who owns the fix. SUCCESS CLIENT_ERROR / *_DUE_TO_MISCONFIG → customer config CLOUD_FAILURE → cloud provider SERVICE_FAULT → escalate to Databricks
Codes to recognise: NETWORK_CONFIGURATION_FAILURE, NPIP_TUNNEL_SETUP_FAILURE, BOOTSTRAP_TIMEOUT(_DUE_TO_MISCONFIG), INSTANCE_UNREACHABLE, DNS_RESOLUTION_ERROR, SUBNET_EXHAUSTED_FAILURE, AWS_INSUFFICIENT_FREE_ADDRESSES_IN_SUBNET_FAILURE, CLOUD_PROVIDER_RESOURCE_STOCKOUT, AZURE_QUOTA_EXCEEDED_EXCEPTION, INIT_SCRIPT_FAILURE, DRIVER_OUT_OF_MEMORY, DRIVER_UNRESPONSIVE, AWS_INACCESSIBLE_KMS_KEY_FAILURE, SECRET_RESOLUTION_ERROR, EOS_SPARK_IMAGE, METASTORE_COMPONENT_UNHEALTHY.
S1. Clusters hang in Pending, then fail: "Node daemon ping timeout in 600000 ms"

Symptom: New or freshly re-networked workspace. The first cluster waits 20-30 min then terminates. The customer's security team "tightened egress".

Ask: Classic only, or serverless/SQL too? What changed (UDR, firewall, proxy, DNS)? Any TLS inspection? Hub-spoke with forced tunnelling?

Where to look: Termination code/type; firewall logs; a test VM in the workspace subnet running nc -zv to the web app (443), SCC relay (443), artifact/log storage (443) and legacy metastore (3306); curl /api/2.0/clusters/spark-versions with a token; openssl s_client -showcerts.

Ranked causes:

  1. UDR/firewall missing control plane, relay or storage routes (0.0.0.0/0 to an NVA with no exceptions)
  2. TLS-inspecting firewall. curl works only with -k, and network-layer logs look clean
  3. Custom DNS not forwarding
  4. SG/NSG egress missing 443 or 8443-8451; NACL denies (AWS)

Fix: Restore the documented ports and FQDNs and exempt them from TLS inspection. Prevention: validated network template; Databricks port/FQDN list kept in firewall-as-code tests; pre-go-live connectivity check.

S2. New Azure VNet-injected workspace cannot reach PyPI / Maven / control plane, older workspaces fine

Ask: When was the VNet created? NAT Gateway attached? SCC/NPIP on?

Where to look: Subnet associations (NAT), NSG delegation rules, UDRs.

Ranked causes: (1) VNet created after 31 March 2026, so it has no default outbound access. (2) Customer deny rules or a UDR to a firewall without Databricks FQDNs. (3) An egress load balancer with SCC causing port exhaustion.

Fix: Azure NAT Gateway on both host and container subnets (it also gives a stable egress IP). Prevention: add explicit egress to the workspace deployment template.

S3. AWS: "failed to launch spark container on instance ... Timed out with exception after 1 attempts"

Ask: Exfiltration-protection firewall? VPC endpoints? Recent SCP changes?

Where to look: VPC endpoint list, endpoint SGs, CloudTrail; aws sts decode-authorization-message on any encoded failure.

Ranked causes: (1) STS blocked, so nodes can't reach the root S3 bucket. (2) The STS endpoint SG does not allow the workspace SG. (3) SCP denies.

Fix: Allow sts.amazonaws.com or add a regional STS VPC endpoint in (or reachable from) the workspace SG. Prevention: endpoint/SG checklist in IaC.

S4. Launch failures at scale: IP exhaustion, quota, stockout, spot

Ask: Instance type, AZ, autoscale max, spot policy, number of concurrent clusters?

Where to look: Termination parameters (carry the cloud error); cloud quota pages; subnet free-IP counts.

Ranked causes: (1) Subnet too small: 2 IPs per node, so a subnet holds about half its usable IPs as nodes (SUBNET_EXHAUSTED_FAILURE, AWS_INSUFFICIENT_FREE_ADDRESSES_IN_SUBNET_FAILURE). (2) vCPU quota (AWS_RESOURCE_QUOTA_EXCEEDED, AZURE_QUOTA_EXCEEDED_EXCEPTION, GCP_QUOTA_EXCEEDED). (3) Capacity (CLOUD_PROVIDER_RESOURCE_STOCKOUT, AWS_INSUFFICIENT_INSTANCE_CAPACITY_FAILURE). (4) Spot limits (AWS_MAX_SPOT_INSTANCE_COUNT_EXCEEDED_FAILURE). (5) INSTANCE_POOL_MAX_CAPACITY_REACHED.

Fix: Raise quota; different instance type/AZ; spot with on-demand fallback and on-demand driver (field names unverified); serverless for critical jobs. AWS subnet CIDRs can't change, so create a new network config. Azure: ask the account team to expand. Prevention: quota alerts, subnet sizing at design time.

S5. Intermittent cluster launch failures after enabling AWS back-end PrivateLink

Ask: Both endpoints created? Private DNS on? Custom resolvers? When did the workspace reach RUNNING?

Where to look: From a working notebook: %sh nslookup <workspace-url> (must return the private IP); a REST call with the notebook token (any HTTP code, even 401/403, proves the path works; a timeout means a network problem); endpoint SG rules.

Ranked causes: (1) One of several resolvers gives public answers. (2) Relay/workspace registrations swapped in the network config, or PAS missing. (3) Endpoint SG missing 443/6666 (2443 with FIPS). (4) Clusters created before the roughly 20-minute wait after RUNNING. (5) VPC DNS hostnames/resolution off.

Fix: Correct DNS forwarding and registrations. Prevention: DNS test in the change runbook.

S6. Azure: browser SSO broken for every workspace in a region, REST/PAT still works

Ask: Any workspace deleted recently? Front-end Private Link in use?

Where to look: Which workspace hosted the browser_authentication private endpoint; private DNS zone records; system.access.audit with service_name='accounts'.

Ranked causes: (1) The workspace hosting browser_authentication was deleted. There is only one per region per private DNS zone. (2) Expired SAML cert or OIDC secret (that breaks all browsers everywhere, not one region). (3) IdP app assignment or conditional-access change.

Fix: Recreate the endpoint in a surviving or dedicated workspace and update DNS. Use emergency-access users if admins are locked out. Prevention: dedicated "private web auth" workspace per production region, with deletion guarded.

S7. Cluster fails with INIT_SCRIPT_FAILURE / GLOBAL_INIT_SCRIPT_FAILURE

Ask: Where is the script stored? Access mode? Anything changed in egress or the global scripts?

Where to look: An INIT_SCRIPTS_STARTED event with no matching INIT_SCRIPTS_FINISHED (event details key global/cluster); logs at <log-path>/<cluster-id>/init_scripts/<cluster-id>_<container-ip>/...sh.stderr.log or /databricks/init_scripts on the node. Events log for one node only, so check every container directory. Audit globalInitScripts events.

Ranked causes: (1) apt/pip blocked by egress. (2) Script on deprecated DBFS. (3) Not on the Standard-mode allowlist. (4) Script bugs: CRLF endings, missing set -e or exit codes general Linux practice.

Fix: Move to a UC volume or workspace files; allowlist; mirror packages. Prevention: lint scripts in CI; consider environments/serverless.

S8. "PERMISSION_DENIED: User does not have USE SCHEMA on Schema 'poc.schema1'" — "but I have SELECT"

Ask: Exact error string? Which principal (a job may run as a service principal)? Compute access mode? Is the catalog bound to specific workspaces? Ownership transferred recently?

Where to look: SHOW GRANTS on catalog, schema and table; group membership (SCIM does not nest); system.access.audit where service_name='unityCatalog' for the denied action and any recent revoke.

Ranked causes: (1) Missing USE CATALOG/USE SCHEMA. (2) Job runs as a different principal. (3) Legacy (non-UC) access mode. (4) Workspace-catalog binding. (5) Raw path access without READ FILES. (6) Row filter / mask / ABAC policy.

Fix: Least-privilege grants to groups. Prevention: grants as code, one databricks_grants per securable.

S9. External location: "java.nio.file.AccessDeniedException: s3://... getFileStatus ... 403 Forbidden"

Ask: Was any IAM role deleted and recreated? KMS-encrypted bucket? Cross-account? Fails on classic, serverless, or both?

Where to look: Bucket policy (look for AROA... strings); storage credential trust policy (sts:ExternalId); KMS key policy; CloudTrail AccessDenied for the role session; "Test connection" in Catalog Explorer.

Ranked causes:

  1. Role deleted and recreated. AWS replaced the ARN in the bucket policy with the old unique ID (AROA...), and a new role with the same name does not get access back
  2. Trust policy sts:ExternalId doesn't match the storage credential's External ID (copy it from the credential; the 0000 placeholder was never updated), or the role isn't self-assuming. Databricks blocks non-self-assuming roles; run Validate Configuration.
  3. KMS key policy missing Decrypt/GenerateDataKey for the UC role
  4. Cross-account bucket policy, SCP or permission boundary
  5. Path outside the external location; VPC endpoint policy / aws:SourceVpce condition (classic-vs-serverless split)

Fix: Replace the AROA ID with the current role ARN and retest. Prevention: manage policies in IaC by ARN reference; alert on IAM role deletion.

S10. Azure: works on classic cluster, 403 on serverless SQL warehouse

Ask: Storage firewall on? Credential type (managed identity or service principal)? NCC configured?

Where to look: Storage account networking (VNet rules, resource-instance rules); access connector role assignments; NCC private endpoints.

Ranked causes: (1) Serverless runs in Databricks' subscription, so the VNet rules don't cover it and no NCC is configured. (2) Missing resource-instance rule for Microsoft.Databricks/accessConnectors. (3) Service principal credential, which can't pass network rules the way a managed identity can. (4) Missing Storage Blob Data Contributor.

Fix: NCC with serverless private endpoints or allowlisted subnets; access connector managed identity. Prevention: include serverless in storage-firewall design reviews.

S11. Lakeflow job intermittently fails: "Driver is temporarily unavailable"

Ask: All-purpose or job compute? Other notebooks attached? Data growth? Any collect/toPandas?

Where to look: Event log Driver_Not_Responding ("likely due to GC"); termination code DRIVER_OUT_OF_MEMORY / DRIVER_UNRESPONSIVE; driver stdout/stderr/log4j GC lines; thread dump; system.compute.node_timeline. Standard mode shows driver logs to admins only.

Ranked causes: (1) Driver-side collection or large broadcast. (2) Shared all-purpose cluster with many notebooks. (3) Single-node pandas/Python loops. (4) Driver too small. (5) DRIVER_UNREACHABLE/network, if GC looks healthy.

Fix: Bigger driver; keep work distributed; job compute or serverless jobs. Prevention: compute log delivery to a UC volume (logs survive termination); scheduled restarts of interactive clusters.

S12. "Databricks broke our pipeline": jobs fail with cast/overflow errors after 15.4 LTS → 17.3 LTS

Ask: Exact before/after DBR versions? Failing run IDs? Did the code change? Are runtimes pinned in job definitions?

Where to look: Release-note behavior-change sections; error class; a canary run of the same job on the old version.

Ranked causes: (1) DBR 17.0 made ANSI SQL the default, so invalid casts, overflow and divide-by-zero now raise errors instead of returning NULL. (2) Library jumps (pandas 1.5.3 → 2.2.3, NumPy 1.26.4 → 2.1.3). (3) pandas-on-Spark blocked under ANSI by default. (4) MERGE APIs (Scala/Python) now return a DataFrame. (5) DBFS custom CA certs unsupported. (6) A real regression → Backline with a repro.

Fix: Pin back to 15.4 LTS (supported to 19 Aug 2027) or set spark.sql.ansi.enabled=false as a temporary bridge. Long term, use try_cast/try_divide. Prevention: pin LTS in bundles/policies; staging canary on the next LTS; read release notes.

12. Technical Q&A

Architecture & networking

1. Explain control plane vs classic vs serverless compute plane, and why it matters for support.
The control plane (web app, REST APIs, scheduler, UC services) lives in Databricks' account. In classic, VMs run in the customer's VPC/VNet, so customer IAM, quotas, subnets, NSGs, SCPs and firewalls are all failure points. Clusters reach the control plane through an outbound 443 tunnel to the SCC relay, with no public IPs. In serverless, compute runs in Databricks' account in the same region. Startup takes seconds and data access goes through NCCs and serverless private endpoints. The plane tells me who owns the failing component and which logs exist: Spark UI and cluster logs on classic, query profile and system tables on serverless.
2. AWS customer-managed VPC: clusters stuck Pending after the security team "tightened egress". Triage?
Scope first. If serverless and SQL warehouses work, it's the customer's network. Pull the termination code and type. Check against the documented egress: 443, 8443/8445 (compute → control plane API), 8444 (UC lineage/logging), 3306 if legacy HMS, 6666 with back-end PrivateLink. Then check NACLs (must not deny), the route table (0.0.0.0/0 → NAT), DNS hostnames/resolution, and that the firewall allowlists relay FQDNs, not IPs. Reproduce with a test cluster or VM using nc/curl. Restore the minimum ports, then RCA it as a change-management gap and add the port list to firewall-as-code tests.
3. What does SCC change, and what's the Azure equivalent?
Secure cluster connectivity is the default for all new workspaces. Nodes have no public IPs and the VPC has no inbound ports. Each cluster opens an outbound HTTPS tunnel to the SCC relay, which is separate from the REST endpoint, and the control plane sends commands down it. Relay reachability is the first check when clusters hang. On Azure it's No Public IP (NPIP), enableNoPublicIp, default true from API 2024-05-01. Upgrading an existing workspace requires stopping all compute.
4. Walk through AWS back-end PrivateLink requirements.
Two interface endpoints, the workspace REST API and the SCC relay, each with private DNS on, in a dedicated subnet with their own SG. Requires a customer-managed VPC, SCC, Enterprise tier, a supported region, DNS hostnames/resolution, and VPC CIDR /25+. Register the endpoints, reference relay and workspace registrations in the network config, and attach a Private Access Settings object. SG allows 443 and 6666 (2443 for FIPS). To verify: nslookup returns the private IP, and a REST call returns any HTTP code. Wait about 20 minutes after RUNNING before launching clusters.
5. Explain Azure front-end Private Link and the browser_authentication pitfall.
Front-end uses a databricks_ui_api endpoint in a transit VNet plus a browser_authentication endpoint for Entra SSO callbacks. Only one browser_authentication can exist per region per private DNS zone, and it serves every workspace there, so best practice is a dedicated web-auth workspace per production region. If someone deletes the hosting workspace, browser login breaks region-wide while REST/PAT keeps working. That asymmetry is the clue. Back-end uses databricks_ui_api in the workspace VNet with requiredNsgRules=NoAzureDatabricksRules.
6. How do you tell a cluster-launch failure that's the customer's fault from one that's Databricks'?
The termination reason type. CLIENT_ERROR or codes ending _DUE_TO_MISCONFIG point to customer config. CLOUD_FAILURE (stockout, quota, launch failure) points to the cloud provider. A burst of SERVICE_FAULT across clusters, especially with a status-page event, means escalate to engineering immediately. I confirm with the termination parameters, which carry the raw cloud error.
7. Where do you look first in a P1 affecting many jobs across a customer's workspaces?
Blast radius and timeline: which workspaces and regions, classic vs serverless. Check status.databricks.com and internal incident channels. Query system.lakeflow.job_run_timeline for when failures began and the common error class. Check system.access.audit for correlated changes: policy edits, permission changes, metastore or external-location changes, token revocation. Ask about cloud-side changes (SCPs, firewall, KMS rotation, NAT). Mitigate, communicate on a fixed cadence, then RCA.

Unity Catalog, identity & governance

8. Walk through UC's storage model.
A storage credential wraps a long-term cloud identity (IAM role, managed identity or service account). An external location pairs a path with a credential, and many locations can share one credential. Tables and volumes sit under locations. Managed tables: UC governs access and lifecycle. External tables: access only. The metastore is one per region, with a catalog.schema.object namespace. Reads need USE CATALOG + USE SCHEMA + SELECT. Raw path reads need READ FILES.
9. What are the access modes today and how do you choose?
Standard (formerly Shared, USER_ISOLATION): multi-user Lakeguard isolation, recommended default, but no RDDs/sparkContext, ML runtime, GPU or R, IMDS blocked, init scripts/JARs allowlisted, and restricted Spark confs on DBR 19+. Dedicated (formerly Single user, assignable to a group): ML, GPU, R, RDDs. Auto (default) picks Standard unless ML runtime, GPU or DBR < 14.3. Legacy modes aren't UC-compatible. In a migration I scan code for RDD, sc. and instance-profile usage to decide which workloads need Dedicated.
10. Explain HMS → UC migration gotchas.
SYNC and the upgrade wizard create external tables only. Managed tables in DBFS/workspace storage need deep clone or CTAS. Table history doesn't migrate, so pre-migration time travel is lost. Views aren't upgraded automatically. External upgrades need a storage credential, external location and CREATE EXTERNAL TABLE. UCX is a Databricks Labs tool and not directly supported. HMS federation is an alternative. Common tickets: DBFS mounts or /dbfs FUSE on Standard compute, RDD code failing on Standard, missing USE CATALOG on the new catalog.
11. A user sees zero rows from a table with a row filter but the admin sees data. Why?
Check compute first. DBR below 12.2 LTS fails securely with no data, and Dedicated mode needs 15.4 LTS+ with serverless enabled. Then the filter UDF: is_account_group_member uses account groups, so a workspace-local group mismatch is a classic cause. With ANSI off, failed casts become NULL and drop rows. Check for an ABAC policy on the catalog or schema via governed tags, which owners can't override. Rule out views, clones or time travel on protected tables.
12. A user exists in Entra and in the Databricks account but can't open the workspace, and group entitlements keep reverting.
With account-level SCIM, provisioning to the account doesn't grant workspace access. The user or group must be assigned to the identity-federated workspace. Reverting is normal: IdP-owned attributes override UI/API changes at the next sync, so change them in the IdP. SCIM doesn't flatten nested groups, but Azure automatic identity management does. If they're mid-migration from a workspace-level connector, warn them not to remove users there before disabling it, or the users get deactivated.
13. SSO is down and admins are locked out. What do you do?
Emergency access first: up to 20 users with password plus security key. Then the usual suspects: expired or rotated SAML x.509 cert or OIDC client secret, a changed redirect URL, users removed from the IdP app, conditional access changes. Get the exact error and a HAR. In system.access.audit, filter service_name='accounts' on samlLogin/oidcBrowserLogin failures to find when they began. Prevention: Test SSO before saving, cert-rotation reminders, tested break-glass users.
14. How would you migrate a customer's CI/CD from PATs to OAuth?
Create an account-level service principal with minimum entitlements and UC grants. Use OAuth M2M, or better, OAuth token federation from the CI's OIDC provider (GitHub Actions, Azure DevOps) so no secret is stored. Configure unified auth (DATABRICKS_HOST/CLIENT_ID/CLIENT_SECRET or a profile) so CLI, SDK, Terraform and bundles all pick it up. Deploy bundles with run_as the SP. Find remaining PAT usage via the token-management API and audit logs, set lifetime limits, then restrict PAT creation.
15. How do you handle a GDPR erasure request on Delta tables?
Drive deletes from a control table of subject IDs with MERGE ... DELETE across bronze/silver/gold. With deletion vectors, run REORG TABLE ... APPLY (PURGE), otherwise rows still exist physically. MVs pick up deletes on refresh. Streaming tables are append-only: delete in source and target and use skipChangeCommits. Old versions stay reachable until VACUUM (7-day default), so the SLA must allow for retention plus VACUUM schedule. Purge upstream copies (Kafka, landing files, OLTP). Record completion as evidence; audit trail is in system.access.audit.

Spark & performance

16. A daily job went from 20 minutes to 2 hours with no code change. Triage?
(1) Compare good vs bad run: input volume, DBR, policy changes, spot loss, DESCRIBE HISTORY for new writers or property changes. (2) Jobs timeline: gaps (driver-bound), retries, a dominant job. (3) Longest stage: Max far above p75 means skew; check spill and shuffle sizes. (4) SQL tab: did a broadcast become a sort-merge join because a dimension grew past the 30 MB AQE threshold? Was file pruning lost? (5) Event log: autoscaling, spot loss, Driver_Not_Responding. (6) Compute metrics: iowait, container memory, outlier node, hot driver. (7) Table health: numFiles, whether predictive optimization ran, stats on filter columns (first 32). Fix, show evidence, add a preventive control.
17. 199 tasks finish in 10 s and one runs 40 min. AQE is on. Why didn't AQE fix it?
AQE splits a partition only if it's larger than both 5× the median and 256 MB, and only for shuffle-based joins (sort-merge and shuffle hash). forceOptimizeSkewedJoin only forces it when it would add an extra shuffle; it does not change which joins qualify. A 200 MB hot partition, a broadcast join, the non-preserved side of an outer join (or either side of FULL OUTER), or skew in an aggregation all escape it. Confirm the join type in the SQL tab. Then lower the thresholds, handle the hot key separately (often NULL), broadcast the small side, salt with two-stage aggregation, use REBALANCE on writes or liquid clustering for layout skew. Validate that Max ≈ p75 afterwards.
18. spark.sql.autoBroadcastJoinThreshold vs spark.databricks.adaptive.autoBroadcastJoinThreshold? When does broadcast hurt?
The first (OSS 10 MB, -1 disables) applies at plan time from estimates. The second (30 MB) is AQE at runtime from real shuffle sizes. Broadcast hurts when estimates are wrong: the table is collected to the driver and copied to every executor, giving "Size of broadcasted table far exceeds estimates...", driver OOM, or a 300 s broadcast timeout. Fix with ANALYZE TABLE, removing the BROADCAST hint, or a MERGE hint, per query. Don't disable broadcast cluster-wide.
19. Distinguish driver OOM from executor OOM on Databricks.
Driver: "spark driver has stopped unexpectedly", "Driver is temporarily unavailable", Driver_Not_Responding "likely due to GC", maxResultSize errors. Fix by stopping driver-side collection, a bigger driver, job compute. Executor: ExecutorLostFailure ... Remote RPC client disassociated, with no YARN message since Databricks doesn't use YARN. Rule out spot/autoscale in the event log, test by doubling memory per core, then fix skew, partitions (auto), broadcasts, UDFs, windows without PARTITION BY, or streaming state (RocksDB).
20. A Kafka stream is falling behind. Diagnose and explain lag to the customer.
Spark doesn't commit offsets to Kafka. The checkpoint is the truth, so their consumer-group lag dashboard misleads. Read avgOffsetsBehindLatest, maxOffsetsBehindLatest and estimatedTotalBytesBehindLatest from StreamingQueryProgress. Compare input vs processed rows per second and batch duration. Bottlenecks: skewed Kafka partitions (minPartitions), expensive state (state size, watermarks), small-file writes, undersized compute. Use maxOffsetsPerTrigger to catch up predictably. startingOffsets doesn't apply to an existing checkpoint. failOnDataLoss=false hides lost data, so set it only as a conscious, documented decision.
21. The customer changed a stream (new aggregation, second topic) and wants to "just delete the checkpoint".
Stateful operator and source changes need a new checkpoint, so the failure is expected. Deleting the checkpoint means either reprocessing everything (duplicates in non-idempotent sinks) or skipping data, depending on startingOffsets. Safer: a new query with a new checkpointLocation, explicit starting offsets where the old one stopped, and an idempotent sink (MERGE or foreachBatch with txnVersion/txnAppId). On DBR 18.2+, source evolution can add named sources but can't be undone. Continuous trigger isn't supported on Databricks; real-time mode replaces it.
22. A SQL warehouse dashboard is "slow". Capacity, sizing or the query?
Monitoring tab: a nonzero Peak Queued Queries is a concurrency shortfall, so raise max clusters (classic/pro guideline: about 1 cluster per 10 concurrent queries; serverless uses IWM). Query profile: high bytes spilled to disk means a bigger size. Query history splits queue, compile and execution time. A slow first query of the day is cold start on classic/pro. If execution dominates, look at data layout: liquid clustering, stats, file sizes, Photon coverage. Max queue is 1,000 queries. A query waiting 5 minutes triggers scale-up on classic/pro.
23. A Lakeflow pipeline (formerly DLT) works in dev but writes duplicates intermittently in prod.
Pipelines evaluate source code several times during planning. Side effects inside dataset functions (collect, count, saveAsTable, external writes, custom monitoring) run repeatedly. Fix: pure definitions that only return DataFrames, sinks or foreach_batch_sink for external writes, event hooks for monitoring. Check event_log flow progress and expectations, and whether prod is continuous vs triggered or serverless vs classic. import dlt still works, but pyspark.pipelines as dp is recommended.

Delta & operations

24. "I accidentally deleted rows. Can you recover?"
DESCRIBE HISTORY to find the pre-delete version. If it's within deletedFileRetentionDuration (7 days) and not vacuumed, RESTORE TABLE t TO VERSION AS OF n (needs MODIFY), or re-insert selectively from a time-travel query. On DBR 18+, time travel beyond deleted-file retention is blocked. Warn that RESTORE is a data-changing commit, so streaming readers may reprocess. Prevention: suitable retention, restricted MODIFY, deep-clone backups of critical tables.
25. Two jobs writing one Delta table keep failing with ConcurrentAppendException.
Optimistic concurrency at WriteSerializable: another commit added files in data my MERGE/UPDATE/DELETE read. Make the operations disjoint with explicit partition or cluster-key predicates in the MERGE ON clause. Enable row-level concurrency (unpartitioned, DVs, DBR 14.3 LTS+). Serialize the jobs or retry idempotently with backoff, and don't overlap OPTIMIZE on the same files. Then tell it apart from DeleteRead, DeleteDelete, MetadataChanged, ConcurrentTransaction (shared checkpoint) and ProtocolChanged.
26. The customer wants VACUUM RETAIN 0 HOURS and asks you to disable the safety check.
Push back and explain the impact. The 7-day window protects long-running readers, streams and uncommitted writers, and 0 hours can break in-flight queries and removes time travel permanently. Disabling retentionDurationCheck removes a safeguard, so it needs explicit sign-off and confirmation that nothing runs longer than the window. Run DRY RUN first. On DBR 18.0+, VACUUM ignores any RETAIN value other than 0 hours, so if they really want a shorter (non-zero) window, change delta.deletedFileRetentionDuration instead. For compliance deletion, the sequence is DELETE → REORG PURGE → VACUUM. For routine cleanup, use predictive optimization or scheduled VACUUM LITE.
27. 2 million small files and slow queries. Recommendation?
Short term: OPTIMIZE (incremental), with WHERE on recent data if huge. Prevent: optimized writes + auto compaction. Find the cause: default streaming trigger micro-batches, high-cardinality partitioning, tiny appends. Long term: liquid clustering; on UC managed tables, let predictive optimization run OPTIMIZE/VACUUM/ANALYZE and drop hand-scheduled jobs. Set expectations that OPTIMIZE FULL can take hours. Verify with DESCRIBE DETAIL numFiles and files-pruned in the query profile.
28. An orchestrator gets intermittent HTTP 429s from the Jobs API.
Per-endpoint, per-workspace limits; error_code is RESOURCE_EXHAUSTED (older material says REQUEST_LIMIT_EXCEEDED legacy, unverified). /jobs/runs/get allows 100/s and /jobs/runs/submit 35/s, so a tight polling loop hits them fast. Fix: exponential backoff with jitter honoring RetryInfo in error details; SDK built-in retries; poll less, use notifications; list-with-filter instead of N gets; system tables for reporting. Workspace limits also include 10,000 jobs created per hour and 2,000 concurrent task runs. Check the limits page before promising an increase.
29. Terraform shows a permanent diff on databricks_permissions.
Two resources manage the same object's ACL, and each apply overwrites the other because they're authoritative. Use one databricks_permissions/databricks_grants per securable with dynamic blocks. Other drift sources: UI edits and server-side defaults. Related errors: "cannot configure default credentials" (add depends_on the workspace), "more than one authorization method configured" (set auth_type), "HTTP method POST is not supported by this URL" (missing account_id on account resources), invalid character '<' (workspace object on an account provider).
30. How would you proactively monitor a customer's platform without third-party tools?
System tables plus Databricks SQL alerts. Jobs: system.lakeflow.job_run_timeline/job_task_run_timeline for failure rate and duration regressions. Pipelines: pipeline_update_timeline. Cost: system.billing.usage. Compute: node_timeline, warehouse_events. Queries: system.query.history. Security: system.access.audit. Alert to email, Slack or webhook; review system.alert.alert_evaluation_history. Mention 395-day retention and grants for non-admins. If they already run Datadog or Azure Monitor, route diagnostics there integration steps unverified.

B1. Why Databricks, and why frontline Platform support rather than SRE or SA?
Platform frontline sits where cloud infrastructure, distributed compute and customer impact meet. Cite the JD's Sev1 ownership with RCA and prevention, "customer obsessed" and "first principles", the fast-moving product (Lakeflow, Lakebase, Agent Bricks), and the org's push to codify troubleshooting into automation and AI skills. B2. Tell me about an incident you led where the RCA changed something permanently.
S: severity and blast radius. T: your role (incident lead). A: separated mitigation from diagnosis, roles and cadence, evidence (logs, metrics, traces), one hard call (roll back vs wait for a hotfix). R: MTTR, customer outcome, and above all the preventive measure (guardrail, alert, runbook, upstream fix, KB article that cut repeat tickets by N%). Name the hypothesis you dropped when the data contradicted it (truth seeking).
B3. An angry customer says Databricks broke their pipeline after an upgrade and wants an engineer on a call now.
Acknowledge impact without blame and confirm severity (Sev1 or MC-Sev depending on plan). Set next steps and cadence. Get on a call if it speeds diagnosis, but run it with structure: what changed, exact DBR before and after, failing run IDs. Mitigate (pin the previous runtime), then diagnose: release-note behavior change, deprecated API, or a real regression going to Backline with a repro. Plain language for leadership, technical detail for engineers. Afterwards recommend staging, pinned runtimes and CI with bundles.
B4. A time you were wrong during troubleshooting.
An early hypothesis (e.g. blaming the network), the data that contradicted it (error only on one runtime version; metrics showing GC pauses instead), how you pivoted, and how you changed your method: falsifiable hypotheses, check change logs first, reproduce before concluding. They want intellectual honesty and a system, not a flawless record.
B5. A Sev1, two Sev2s and a Sev3 backlog at the end of your shift.
Severity and SLA drive order. The Sev1 gets active work and a documented hand-off to the next region: status, next steps, named owner. Sev2s get current updates and next actions. Ask the manager or duty lead to rebalance rather than letting SLAs lapse quietly. Batch Sev3 updates with honest timelines. No customer goes without an update, and hand-off notes must be actionable without contacting you.
B6. Disagreement with engineering ("works as designed").
Minimal repro, quantified impact (tickets, affected workloads), framed against documented expected behavior. Offer options (docs fix, config flag, product change), not an ultimatum. Disagree and commit if overruled, but get a documented workaround and KB article. Result: fix shipped or docs clarified, ticket volume down.
B7. Automation or process improvement that reduced toil.
A log-triage script, a diagnostic collector for cluster events and driver logs, a ticket-classification/deflection KB, or an LLM-assisted runbook. Before and after: handle time, repeat-ticket rate, escalation rate. Tie it to "raise the bar" and "bias for action", and to Databricks' own push to turn failure patterns into tooling and Claude skills. Mention guardrails: validation and no customer-data leakage.
B8. Explain a complex root cause to a non-technical executive.
Business impact and status first, then a one-sentence plain cause, what was done, what prevents recurrence, and any action needed, with dates. Example: "executor OOM from skewed shuffle partitions" becomes "one step of the nightly job received far more data than expected and ran out of memory; we rebalanced it and added an alert." Technical detail goes in a separate engineer-to-engineer note.
